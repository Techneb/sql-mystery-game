# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Browser SQL game for an SQL course. Spec: `docs/superpowers/specs/2026-09-20-sql-mystery-game-design.md`; plans in `docs/superpowers/plans/`.

## Commands

```bash
python3 generate_db.py                  # rebuild site/ outputs + solution.sql; fails if the plot breaks
python3 generate_db.py --season 3       # compete season: site/season-3.{sqlite,json} (gitignored)
python3 generate_db.py --seasons         # every compete database (generate_db.SEASONS = 5), what the deploy builds: run before every push
python3 -m unittest -v                  # Python suite (test_generate.py), ~2 min: it rebuilds the database
python3 -m unittest test_generate.Discovery.test_row_count_passes_and_fails   # one test
node --test test_site.mjs               # site pure functions, imports site/app.js directly, < 1 s
node --test test_backend.mjs            # apps_script.gs in a vm with stubbed Google services (a Sheet that coerces like the real one)
node --test --test-name-pattern normalise test_site.mjs                      # one site test
python3 -m http.server 8000 -d site     # play at localhost:8000 (file:// fails); ?selftest checks the fixture
```

Pages deploys `site/` on every push to `main` (`.github/workflows/pages.yml`, which first builds the five compete databases) to <https://mystery.alephb.uk> (custom domain; DNS and the alephb.uk home page are managed from the owner's Compromise project, not here). A push is a live deploy to students: the course owner approves each one.

## Architecture

Python side (build time) -> static files -> browser side (runtime, no server):
- `plot.py` (story + SQL as data) and `generate_db.py` (values per seed, schema, noise, planting, self-checks) write `site/mystery.sqlite`, `site/chapters.json`, `site/schema.svg` (via `erd.py`) and `solution.sql` (it opens with the answer key in play order, the Part II code after chapter 8, then each chapter's discovery queries and solution). Generated files are committed because the site is static.
- `site/app.js` is one ES module: loaded by `index.html` in the browser (with sql.js from cdnjs) and imported by `test_site.mjs` in node, so pure logic is `export`ed and browser globals (`localStorage`, `document`) stay inside functions. `site/shared.js` (side-effect free) holds what the game, the admin page and the board share: `normalise`, `sha256`, `teamKey`, `ADMIN_PASS_SHA256`, `officialTime`, `chapterSummary`, `fmtTime`, `escapeHtml`; `app.js` imports it and re-exports what the tests import.
- Answers are checked client-side against hash lists (`answer_sha256`: `sha256(normalise(answer))` plus the surname alone for name answers; `part2_code_sha256`: the code with and without its leading STOP) in `chapters.json` and in each season file, never plaintext.
- Compete: `apps_script.gs` is the Google Apps Script backend holding the season records and the event rows; the game posts to it, `site/admin.html` manages seasons and `site/leaderboard.html` reads it.

## Invariants (the build or a test enforces these)

- Stdlib only, no build step. `python3 generate_db.py` rebuilds `site/` outputs and **is the test of the plot**: every solution must return exactly its answer and every trap must bite (the naive query, and each query in a chapter's optional `traps` list, must not yield the answer). `python3 -m unittest -v` pins the same plus normalisation and ERD layering.
- Any text or data must be pure ASCII: `LC_ALL=C grep -n '[^ -~]' plot.py generate_db.py erd.py solution.sql site/chapters.json` must print nothing.
- Never edit `site/chapters.json`, `site/schema.svg` or `solution.sql` by hand. Adding a chapter = one dict in `plot.CHAPTERS` (text + `solution` + `naive`) and its planting in `plant_part2`.
- Answer normalisation lives twice: `generate_db.normalise` and `site/app.js normalise`; `chapters.json.normalise_fixture` is checked by the page in `?selftest` mode. Change both together. Rules: lowercase `[a-z0-9]+` tokens; a lone letter glues to the digits after it before stop words go ("A-7", "A 7", "A7" -> "a7"); stop words include titles, honorifics and labels (lord, mr, m, monsieur, madame, countess, suite, room, trunk, wire, id, report, account, plate, paris...); a trailing "stop" goes when more than one token remains; all-digit answers are joined and lose leading zeros. The fixture must never contain a planted value or a cast name.
- Every Part I chapter withholds a constant and carries a `discovery` list (`discovery_compete` for the compete objective): `check_discovery` runs each query at build time and asserts the withheld fact is in the result (`must_contain`, case-insensitive) or the row count (`row_count`). A chapter whose clue stops being discoverable fails the build. `solution.sql` prints the discovery queries before the final one.
- Chapter stories never quote an earlier chapter's answer literally (the JSON ships every chapter); they say "the plate you found in chapter 3".
- Never refer to a planted row by a literal id outside `plant_part1` / `plant_part2` (see the id scheme under Plot and data).
- Debug entry points are gated: `?chapter=N` and the `?admin` panel both ask for a passphrase (`#passgate`, a native `<dialog>` with a password field, never `prompt()`) checked against `ADMIN_PASS_SHA256` in `site/shared.js` (sha256 of the trimmed, lowercased passphrase, the form `apps_script.gs` compares; never the answer normaliser, whose rules change; the passphrase itself is never in the repo, ask the course owner). Neither writes to localStorage. A jump marks the earlier chapters solved without an answer, so their case board cards show the label alone: the page only has the answer hashes, and the owner declined (2026-10-09) an answer key encrypted with the passphrase and published by the deploy; do not propose it again.
- Never commit a deployment URL (the Apps Script `/exec` URL is a live, unauthenticated write endpoint; it travels in links).
- Cache: the deploy step rewrites the scripts and stylesheets of index.html, privacy.html, admin.html and leaderboard.html (`app.js`, `admin.js`, `leaderboard.js`, `style.css`, `admin.css`, `learn/learn.css`) and the `shared.js`/`qr.js` imports of `app.js`, `admin.js` and `leaderboard.js` to `?v=<commit>`; any page or module importing `shared.js` or `qr.js` must be in those two lists (a test checks the current ones). `app.js` fetches its data files with the same query (`VERSION`), so a page never runs a stale cached script against new markup or data. Fetch any new same-site data file with `+ VERSION`.
- `site/privacy.html` describes exactly what leaves the browser (compete `join`, `eventPayload` with `clientAt`/`elapsedMs`, the 5 s season poll, the join token, the fonts/cdnjs/Pages requests, GA4 behind consent). Change it whenever what the game sends or loads changes. Its Advertising section carries Google's required AdSense wording and says no ad script is loaded yet; update it when ads go live (consent message, how to withdraw).
- Analytics: GA4 `G-QG0K0D1NQZ` (`GA_ID` in `site/app.js`, public), loaded only after a Yes on the `#consent` banner (`ritz.consent`; the footer's Statistics link reopens it; No deletes the `_ga` cookies), Consent Mode v2 with everything denied by default. Events go through `track(name, params)` only: `chapter_open`, `chapter_solve` (seconds, queries, wrong), `game_finish`, `badge`; never the pseudo, answers or queries; off in `?chapter=N` debug mode. `?ga=G-XXXX` overrides the ID on localhost only. The GA property keeps 14 months and granular location (privacy.html says so); its custom definitions are registered.
- Ads: AdSense `pub-9765732642926043` on `alephb.uk` (approval pending; verification tag in `index.html`, `ads.txt` on alephb.uk). The ad box (`#ad-box`, a `<details>` under the schema, open by default, closed state in `ritz.ads`) stays hidden until `ADS_ON`; preview at `localhost:8000/?ads=1`. What is left after approval is in the spec's backlog (Advertising). The landing card's `<details class="landing-about">` (closed by default) is the crawlable prose (with the meta description) a reviewer or a no-JS crawler reads: chapter titles and constructs only, never a clue, answer or withheld detail.

### Shortcut check

**Every puzzle is checked for shortcuts before it ships** (course owner, 2026-10-02: "always think of such when crafting problems"). For each chapter, try:
1. what the student already knows (earlier answers, telegrams, suspect cards and notes, stories, landing page) and whether it names the answer directly (an account number, initials, a suite);
2. LIKE on every word the story or landing page offers;
3. the obvious one or two filters, and small results to eyeball (a lone row, an odd weight, a lone ticket);
4. the plausible guess ("a thief wires at night", "the earliest champagne");
5. whether the taught construct is actually needed.

Each shortcut found becomes a decoy in the data and a query in the chapter's `traps`, so the build keeps it closed. Pinned so far:
- ch1 keyword LIKEs (Comtesse, sapphire, Blue Star, balcony, A. L., porter, lift, Duroc, pillow, calling card), each also with Ritz + theft, all answered only by the date;
- ch2 ORDER BY price without the date;
- ch3 pound fares without or on the wrong date;
- ch6 SUM without the count, ownerless accounts, PAYMENT wires;
- ch7 the night guess, the R. letter alone, the busiest box;
- ch8 the wire's suite, the earliest champagne;
- ch9 a trunk alone on its ticket, a holder seen once (his valet and maid, Hobbs and Pringle, hold their own tickets), any holder but Ashcombe;
- ch10 suite 214's guests, price 150, six-night stays;
- ch11 the lift around 02:10, a gap of exactly one hour spanning 02:10 (noise lift rounds are 01:30 / 02:20 / 03:30, so only 214's 65 minutes spans it; the last noise floor-2 suite skips the 03:30 round so the naive lift count still returns two suites; Velmont rings 01:50, 02:30, 05:55);
- ch1 and ch6 `ORDER BY id DESC LIMIT 1` (compete too); ch9 `address_id IS NULL`; ch10 `occupation = 'gentleman'` (Grey is a rentier, the noise has gentlemen); ch12 big transfers after the theft by date (12 noise transfers of 20-40 kF run 21 May-13 June), owned accounts above 60000, MAX(id); compete ch3 `dropoff_address_id IS NULL`.

Known and accepted: ch11's answer is Lupin's suite, already known from ch8.

## Plot and data (`plot.py`, `generate_db.py`)

- `plot.py` is data; `V` (planted values) is drawn in `plant_values(seed)`; seed 1912 pins the learning-mode values quoted in the story and objective text.
- Stories and endings carry `**bold**` (a person at first mention in that chapter, plus at most one phrase saying what to find; two or three runs a story, never a clue value or a hint toward one) and `*italic*` (every quoted line as one run, quotation marks inside; named documents and institutions; a few existing atmospheric asides; a hint outside a quote stays plain), rendered by `richText` in `site/app.js` (escapes first, then only those two marks; a test checks every story's markup is balanced). A blank line (`\n\n`) starts a paragraph and a block of `| cell | cell |` lines becomes a table, first row the header (ch7's four boxes, ch12's road): use them to keep each story short paragraphs, facts in a table.
- Never emphasise clue values (times, amounts, dates, places searched for): objectives are deliberately bare (ch. 1 is only "Mr Duroc knows which night.") and formatting must not hand the clue back.
- Noise names echo the noise lines' references: `GUESTS` (full names, 1912 dress) fill `hotel_register`, `interview`, `luggage` and `telegram`; the census (`person`) mixes `FIRST` x `LAST`. Tests keep planted and cast names out of `GUESTS`, planted surnames out of `LAST`, and no apostrophes or `FILM_LINES` fragments in guest names. Noise report text carries no reporter name: the planted reports have none, so it would single them out.
- Times (`cab_ride`, `telegram`, `room_service`, `lift_log`) are planted as HHMM integers and turned into `'HH:MM'` text by `clock_times` at the end of `build_db`; plot SQL compares them as text (`time < '06:00'`).
- `cab_ride.currency` (mostly franc) carries chapter 3's clue: Ashcombe's valet saw the man tip in English coins, so the night cab is the one 75-2 plate paid in pounds on the 18th (a pound fare from Vendome on the 17th is the decoy).
- Ids: noise ids start at 100 in every table; planted rows are inserted with ids below 100 or in blocks above the noise, and every id pinned in `V` is drawn inside its table's noise range (reports 1000-2999, accounts 1000-3999; learn 2127 / 1200 / 2170 / 3213 / 1540 / 2740). `scatter_planted` then swaps every planted id with a random mid-table noise row (foreign keys follow), except the `V`-pinned ids and telegram 9001 (the Part II code wire stays MAX by design), so neither `SELECT *` nor `ORDER BY id DESC` nor an id range lists the plot (`test_pinned_ids_hide_among_the_noise`).
- Links between tables: `suite` is the hub of the four Ritz ledgers (`hotel_register`, `room_service`, `lift_log`, `telegram`; noise only ever draws real suites). `link_tables` (after `scatter_planted`, before `clock_times`) adds `interview.person_id` (hotel guests join the census, unnamed witnesses stay NULL), `cab_ride.dropoff_address_id` (stations NULL) and `guest_card` (1:1 with `person`, fun only, none for the cast; a test checks). Every planted hotel stay goes through `book`, which clears the suite first: no two stays ever overlap in a suite.
- Missing values are NULL, never a 'none' string (e.g. `person.occupation`). The noise carries the same NULLs as the plot so `IS NULL` singles nothing out: 5% of fares drop at a station (NULL `dropoff_address_id`), unnamed `WITNESSES` give interviews (NULL `person_id`), some census rows lack `born_year` or `address_id`.
- The Comtesse has a stay (suite 210 in learn, 15-22 May, 180 F, `others[4]`): the victim is in the register. Grimaud's three pieces to the shell account are dated 16-18 May, before Lupin's "PAYMENT RECEIVED" wire of the 18th and the arrest of the 20th. The stone leaves on the boat train of the 19th (the Part I ending says so); Lupin walks out of the Depot on the 21st (ch IX story), which is why he can write from London.
- Suspects (`plot.CAST`): each is a decoy somewhere (Ortega: the 06:20 wire signed R. in ch7 and champagne after coffee in ch8; Almagro and Sernine: regulars who crossed Blakeney once in ch10; Velmont: the longer, later silence in ch11). A test keeps `notes` free of the clues and answer of the chapter they appear in.
- Case board cards read `ROMAN label answer`: each chapter's `board` label in `plot.py` (`board_compete` where compete asks for something else) says what the answer is ("Licence plate", "Fence's address"...); shown only once solved, so it may name the answer's role in the story.
- Easter-egg badges match lowercase fragments of noise lines in `generate_db.py` (`FILM_LINES`, "a madeleine missing", "rosebud"): keep those lines verbatim.
- Course folder is `../SQL` (not a git repo). `3-Corrections/8. Correction SQL Mystery Game.sql` there is generated by `write_outputs` when the folder exists.

G.), so neither hour nor text gives his away, and Ortega's own R. is in the morning. The letter R. is given only by Ortega's suspect card (met in ch7; a test keeps it out of the chapter's own text). - After each `renderErd`, `showCurrentTables` scrolls the schema box (its `scrollTop`, never `scrollIntoView`, which would move the page) to the topmost `.current` table (smallest translate y, not DOM order) when they do not all fit in the box (chapter 7's telegram was under the fold). Only newly revealed tables are ever outlined: the owner decided (2026-10-09) that the schema never points at the tables a chapter's solution uses, so chapters 4, 10 and 12 outline nothing; do not propose it again.
- `erd.py` lays the rows out in reveal order (`erd.layout(tables, fks, chapters)`, `chapters` = each chapter's `tables` from `plot.CHAPTERS`, the lists `chapters.json` ships): each chapter's new tables are appended after the rows of earlier chapters (`PER_ROW = 2`, a parent before its child within a chapter), so the tables shown up to any chapter are always the top rows, `fitErd`'s crop stays compact and tables never move when later chapters add rows (a test checks). A table fills the last row's free slot unless a table it is linked to sits there (a line never joins two tables of one row); in a new row it goes in its placed parent's column, else on the left.
- Keys are icons (gold primary, silver foreign, the `#erd-key` symbol, legend under the schema in `index.html`, one `data-legend` span per entry), never `->` labels; each line is red with a dot and its cardinality at each end (1 / N, read from the data), coloured by `--rel` (a lighter red in the night edition, where the day red vanished).
- The legend adapts to the visible schema: after each `renderErd`, `renderLegend` summarises the svg (a visible table with a `.key.fk`, each visible `g.fk` line's two labels) and the pure `legendEntries` (tested) picks the entries: primary key always, foreign key, one-to-many when a line has an N, one-to-one when a line reads 1 at both ends (`guest_card` to `person`).
- Every relationship line is straight legs with smooth rounded turns (radius 8): each leaves its parent from its own point (right half of the bottom edge), enters its child at its own point (left half of the top edge), and crosses each gap between rows, and a gutter, in its own lane. A child revealed before its parent (interview above person, cab_ride above address) sits above it and its line runs upward, the mirror image: out of the parent's top edge, into the child's bottom edge, the 1 / N marks on those edges. A line that stays in its column runs down that column's outer side (`MARGIN`), one that changes column down the middle or round either outer side, whichever crosses less (`erd.fk_paths`, which orders exits, entries and lanes and tries every side and lane order in each gutter for the fewest crossings, `erd.crossings`; interview's line goes round the right). Tests check no line crosses a table, no two lines overlap, and no two lines cross.

## Compete

Design: `docs/superpowers/specs/2026-10-10-compete-admin-design.md`.

- Seasons are records in the `SEASONS` Script Property: `{id, name, date, db, penalty, state, createdAt, openedAt, closedAt}`, state `created` -> `open` -> `closed` (or `created` -> `closed` for a season created by mistake, which frees its database), never back. `db` (1-5) is the pre-built database it plays (`site/season-<db>.*`, gitignored, built by every deploy); a new season takes a never-used database, else the one closed longest ago. The admin page creates, edits (while created), opens and closes them with the passphrase as `key` (`ADMIN_KEY`).
- Entry: `index.html?season=<id>&board=<Apps Script /exec URL>`. Boot reads `?meta=<id>` (an unknown season and an unreachable backend read differently on the landing); Join posts `join` (refused: `pseudo taken`, `session closed`, `busy, try again` when the script lock is held, retried once after 2 s, then "press Join again"); a created season shows the waiting card, which polls `?meta` 5 s after each answer; the clock runs from `openedAt` (`state.startedAt` = `clockStart(meta)`: `?meta` and the join reply carry the server's `now`, so a wrong browser clock cancels out), so every clock starts together and a late joiner's already runs. Without the link, a reload resumes an unfinished game only while its season is not closed. A reload resumes from `ritz.compete` (season id, team, token, db, board, openedAt) and re-reads `?meta` once. The masthead reads "Season: <name>"; a post refused with `session closed` adds THE SESSION IS OVER and the game stays playable.
- `RANKS` and `TAUNTS` are constants in `app.js`; `PENALTY.wrong` comes from the season record. The in-game `?admin` panel keeps the chapter jumps, the board URL field and a link to `admin.html?board=<url>`.
- Backend (`apps_script.gs`): every POST is validated (pseudo 1-40 chars, chapter 0-8, wrong 0-2000, queries 0-20000, `clientAt` and `elapsedMs` non-negative integers or an empty cell); the pseudo and season id are written as text (a leading apostrophe), so the Sheet never turns "007" into 7 or a pseudo into a formula; any exception comes back as `{ok:false, error}` JSON; `join` returns a token (HMAC of `teamKey|season id`, `TOKEN_SECRET` or `ADMIN_KEY` or `SHEET_ID`) that `progress` and `finish` carry, accepted only while the season is open; a `finish` needs seven `progress` rows first; a script lock guards join (the duplicate check and the append, then `SpreadsheetApp.flush()`) and the admin writes; `create` makes the log tab, so joins never race to create it. `test_backend.mjs` runs the script against stubs. Rows keep the Sheet's columns (`season` holds ids, `hints` always 0). A refusal (`ok:false`) drops the row; only network failures retry.
- Official time = server finish - `openedAt` + wrong x penalty; "?" when it disagrees with the browser's `elapsedMs` by more than a minute (`officialTime` in `shared.js`). Compete is honour-based (answers are checked in the browser): keep it off the marks.
- Learn and compete progress are separate localStorage keys (`ritz.learn`, `ritz.compete`). Never push to `main` during a timed session: every deploy rebuilds the live databases.
