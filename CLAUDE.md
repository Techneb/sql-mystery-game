# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Browser SQL game for an SQL course. Spec: `docs/superpowers/specs/2026-09-20-sql-mystery-game-design.md`; plans in `docs/superpowers/plans/`.

## Commands

```bash
python3 generate_db.py                  # rebuild site/ outputs + solution.sql; fails if the plot breaks
python3 generate_db.py --season 3       # compete season: site/season-3.{sqlite,json} (gitignored)
python3 generate_db.py --seasons         # every compete database (generate_db.SEASONS = 5), what the deploy builds: run before every push
python3 -m unittest -v                  # Python suite (test_generate.py), ~40 s: one cached build per seed
python3 -m unittest test_generate.Discovery.test_row_count_passes_and_fails   # one test
node --test test_site.mjs               # game, terminal, strict checker, deploy versioning; imports the site's modules directly, ~2 s
node --test test_desk.mjs               # admin, board, QR, monitor, explore, the desk's pages
node --test test_handbook.mjs           # learn pages: chrome, pagers, sitemap, colour_learn.mjs, examples, exercises
node --test test_backend.mjs            # apps_script.gs in a vm with stubbed Google services (a Sheet that coerces like the real one)
node --test --test-name-pattern normalise test_site.mjs                      # one site test
node version_site.mjs abc1234 <copy of site>   # what the deploy runs on site/ (in place): never on the repo's site/
python3 -m http.server 8000 -d site     # play at localhost:8000 (file:// fails); ?selftest checks the fixture
```

Pages deploys `site/` on every push to `main` (`.github/workflows/pages.yml`, which first builds the five compete databases) to <https://mystery.alephb.uk> (custom domain; DNS and the alephb.uk home page are managed from the owner's Compromise project, not here). A push is a live deploy to students: since 2026-10-19 the course owner lets Claude push without asking once the work is tested and checked (never during a timed session); say what each push contained.

## Architecture

Python side (build time) -> static files -> browser side (runtime, no server):
- `plot.py` (story + SQL as data) and `generate_db.py` (values per seed, schema, noise, planting, self-checks) write `site/mystery.sqlite`, `site/chapters.json`, `site/schema.svg` (via `erd.py`) and `solution.sql` (it opens with the answer key in play order, the Part II code after chapter 8, then each chapter's discovery queries and solution). Generated files are committed because the site is static.
- The browser side is plain ES modules, each side-effect free at import with its pure logic `export`ed for the node tests (browser globals stay inside functions; batch 1 of the 2026-10-25 review split them out of `app.js`): `site/app.js` the game page only (state storage and `save`, chapter flow, `runQuery`'s bookkeeping, case board, schema diagram, the compete client, `boot`; it boots only where `#landing` exists); `site/state.js` the saved state (`freshState`, `migrateSave`, the one migration point `loadFrom` uses, `currentChapter`, `visibleTables`, `partStats`...); `site/strict.js` the strict checker and rewriter (`strictCheck`, `toSqlite`, `ilike`, `ymd`, `STRICT_SECTIONS`, `SQLITE_FUNCS`); `site/terminal.js` the SQL terminal of all three surfaces (the game, its prologue, `learn/exercises.html`): one run pipeline `runSql(db, sql, schema, cols, join)` returning `{ res, error, strict, help, note, outcome }` (comma-join guard, strict check, sql.js, `sqliteHelp`, the date note; `outcome` is what GA's `exercise_run` and `query_fail` read), `runHtml`, `runInfo`, one editor `wireEditor(ta, hl, { run, cols, minHeight })` (colouring, Tab completion, Ctrl+Enter, Ctrl+F with the caret at the end, Tab indent, Enter keeping the line's indent; owner, 2026-10-25: the same on all three), `highlightSql`, `formatSql`, `suggestSql`, `blankLiterals`, `columns`, `renderResults`, `terminalDb`, `openSqlJs`, `readSchema`, `pushHistory`; `site/ui.js` widgets (`esc`, `btnLike`, `ICON_ATTRS`, `themeButtonHtml`, `erdButtonHtml`, `setIconButton`, `showCallouts`, `richText`); `site/onboarding.js` the prologue and chapter I's callouts (`state.onboarding`: prologue, tour, done); `site/badges.js` `BADGES`, the eggs and `rank`; `site/suspects.js` the suspects, `portraitSrc` and `cardPicture`; `site/endings.js` the extra editions, films, certificate and share line (taking `(state, data, hooks)`). `learn/exercises.js` imports `terminal.js`, `strict.js`, `ui.js`, `stats.js` and `shared.js`, never the game. `site/shared.js` (side-effect free) holds what the game, the admin page and the board share: `normalise`, `sha256`, `teamKey`, `ADMIN_PASS_SHA256`, `officialTime`, `chapterSummary`, `fmtTime`, `escapeHtml`. - Answers are checked client-side against hash lists (`answer_sha256`: `sha256(normalise(answer))` plus the surname alone for name answers; `part2_code_sha256`: the code with and without its leading STOP) in `chapters.json` and in each season file, never plaintext.
- Compete: `apps_script.gs` is the Google Apps Script backend holding the season records and the event rows; the game posts to it, `site/admin.html` manages seasons and `site/leaderboard.html` reads it.

## Invariants (the build or a test enforces these)

- Stdlib only, no build step. `python3 generate_db.py` rebuilds `site/` outputs and **is the test of the plot**: every solution must return exactly its answer and every trap must bite (the naive query, and each query in a chapter's optional `traps` list, must not yield the answer). `python3 -m unittest -v` pins the same plus normalisation and ERD layering.
- Any text or data must be pure ASCII: `LC_ALL=C grep -n '[^ -~]' plot.py generate_db.py erd.py solution.sql site/chapters.json` must print nothing.
- Never edit `site/chapters.json`, `site/schema.svg` or `solution.sql` by hand. Adding a chapter = one dict in `plot.CHAPTERS` (text + `solution` + `naive`) and its planting in `plant_part2`.
- Answer normalisation lives twice: `generate_db.normalise` and `site/shared.js normalise`; `chapters.json.normalise_fixture` is checked by the page in `?selftest` mode. Change both together. Rules: lowercase `[a-z0-9]+` tokens; a lone letter glues to the digits after it before stop words go ("A-7", "A 7", "A7" -> "a7"); stop words include titles, honorifics and labels (lord, mr, m, monsieur, madame, countess, suite, room, trunk, wire, id, report, account, plate, paris...); a trailing "stop" goes when more than one token remains; all-digit answers are joined and lose leading zeros. The fixture must never contain a planted value or a cast name.
- Every Part I chapter withholds a constant and carries a `discovery` list (`discovery_compete` for the compete objective): `check_discovery` runs each query at build time and asserts the withheld fact is in the result (`must_contain`, case-insensitive) or the row count (`row_count`). A chapter whose clue stops being discoverable fails the build. `solution.sql` prints the discovery queries before the final one.
- Chapter stories never quote an earlier chapter's answer literally (the JSON ships every chapter); they say "the plate you found in chapter 3".
- Never refer to a planted row by a literal id outside `plant_part1` / `plant_part2` (see the id scheme under Plot and data).
- Debug entry points are gated: `?chapter=N` and the `?admin` panel both ask for a passphrase (`#passgate`, a native `<dialog>` with a password field, never `prompt()`) checked against `ADMIN_PASS_SHA256` in `site/shared.js` (sha256 of the trimmed, lowercased passphrase, the form `apps_script.gs` compares; never the answer normaliser, whose rules change; the passphrase itself is never in the repo, ask the course owner). Neither writes to localStorage. A jump marks the earlier chapters solved without an answer, so their case board cards show the label alone: the page only has the answer hashes, and the owner declined (2026-10-09) an answer key encrypted with the passphrase and published by the deploy; do not propose it again.

### Shortcut check

**Every puzzle is checked for shortcuts before it ships** (course owner, 2026-10-02: "always think of such when crafting problems"). For each chapter, try:
1. what the student already knows (earlier answers, telegrams, suspect cards and notes, stories, landing page) and whether it names the answer directly (an account number, initials, a suite);
2. LIKE on every word the story or landing page offers;
3. the obvious one or two filters, and small results to eyeball (a lone row, an odd weight, a lone ticket);
4. the plausible guess ("a thief wires at night", "the earliest champagne");
5. whether the taught construct is actually needed.

## Plot and data (`plot.py`, `generate_db.py`)

- `plot.py` is data; `V` (planted values) is drawn in `plant_values(seed)`; seed 1912 pins the learning-mode values quoted in the story and objective text.
- Stories and endings carry `**bold**` (a person at first mention in that chapter, plus at most one phrase saying what to find; two or three runs a story, never a clue value or a hint toward one) and `*italic*` (every quoted line as one run, quotation marks inside; named documents and institutions; a few existing atmospheric asides; a hint outside a quote stays plain), rendered by `richText` in `site/ui.js` (escapes first, then only those two marks; a test checks every story's markup is balanced, `story_compete` too). A blank line (`\n\n`) starts a paragraph and a block of `| cell | cell |` lines becomes a table, first row the header (ch7's four boxes, ch12's road): use them to keep each story short paragraphs, facts in a table.
- Never emphasise clue values (times, amounts, dates, places searched for): objectives are deliberately bare (ch. 1 is only "Mr. Duroc knows which night.") and formatting must not hand the clue back.
- Noise names echo the noise lines' references: `GUESTS` (full names, 1912 dress) fill `hotel_register`, `interview`, `luggage` and `telegram`; the census (`person`) mixes `FIRST` x `LAST`. Tests keep planted and cast names out of `GUESTS`, planted surnames out of `LAST`, and no apostrophes or `FILM_LINES` fragments in guest names. Noise report text carries no reporter name: the planted reports have none, so it would single them out.
- Times (`cab_ride`, `telegram`, `room_service`, `lift_log`) are planted as HHMM integers and turned into `'HH:MM'` text by `clock_times` at the end of `build_db`; plot SQL compares them as text (`time < '06:00'`).
- `cab_ride.currency` (mostly franc) carries chapter 3's clue: Ashcombe's valet saw the man tip in English coins, so the night cab is the one 75-2 plate paid in pounds on the 18th (a pound fare from Vendome on the 17th and a franc fare from Vendome at 02:30 on the 18th are the decoys).
- Ids: noise ids start at 100 in every table; planted rows are inserted with ids below 100 or in blocks above the noise, and every id pinned in `V` is drawn inside its table's noise range (reports 1000-2999, accounts 1000-3999; learn 2127 / 1200 / 2170 / 3213 / 1540 / 2740). `scatter_planted` then swaps every planted id with a random mid-table noise row (foreign keys follow), except the `V`-pinned ids and telegram 9001 (the Part II code wire stays MAX by design), so neither `SELECT *` nor `ORDER BY id DESC` nor an id range lists the plot (`test_pinned_ids_hide_among_the_noise`).
- Links between tables: `suite` is the hub of the four Ritz ledgers (`hotel_register`, `room_service`, `lift_log`, `telegram`; noise only ever draws real suites). `link_tables` (after `scatter_planted`, before `clock_times`) adds `interview.person_id` (hotel guests join the census, each trading ids with a random noise person so their ids spread like the cast's: at the top of the table they let any other table's id meet only the cast's, `test_id_joins_across_tables_do_not_list_the_plot`; unnamed witnesses stay NULL), `cab_ride.dropoff_address_id` (stations NULL) and `guest_card` (1:1 with `person`, fun only, none for the cast; a test checks). Every planted hotel stay goes through `book`, which clears the suite first: no two stays ever overlap in a suite.
- Missing values are NULL, never a 'none' string (e.g. `person.occupation`). The noise carries the same NULLs as the plot so `IS NULL` singles nothing out: 5% of fares drop at a station (NULL `dropoff_address_id`), unnamed `WITNESSES` give interviews (NULL `person_id`), some census rows lack `born_year` or `address_id`.

- Keys are icons (gold primary, silver foreign, the `#erd-key` symbol, legend on the SCHEMA row, right-aligned, Enlarge beside the label, in `index.html` (owner, 2026-10-25), one `data-legend` span per entry), never `->` labels; each line is red with a dot and its cardinality at each end (1 / N, read from the data), coloured by `--rel` (a lighter red in the night edition, where the day red vanished).
- The legend adapts to the visible schema: after each `renderErd`, `renderLegend` summarises the svg (a visible table with a `.key.fk`, each visible `g.fk` line's two labels) and the pure `legendEntries` (tested) picks the entries: primary key always, foreign key, one-to-many when a line has an N, one-to-one when a line reads 1 at both ends (`guest_card` to `person`).
- Every relationship line is straight legs with smooth rounded turns (radius 8): each leaves its parent from its own point (right half of the bottom edge), enters its child at its own point (left half of the top edge), and crosses each gap between rows, and a gutter, in its own lane. A child revealed before its parent (interview above person, cab_ride above address) sits above it and its line runs upward, the mirror image: out of the parent's top edge, into the child's bottom edge, the 1 / N marks on those edges. A line that stays in its column runs down that column's outer side (`MARGIN`), one that changes column down the middle or round either outer side, whichever crosses less (`erd.fk_paths`, which orders exits, entries and lanes and tries every side and lane order in each gutter for the fewest crossings, `erd.crossings`; interview's line goes round the right). Tests check no line crosses a table, no two lines overlap, and no two lines cross.

## Compete

Design: `docs/superpowers/specs/2026-10-10-compete-admin-design.md`. The admin page `admin.html` ("The Clerk's Desk") is reachable from the footer of the landing card, every handbook page and privacy.html.

- Seasons are records in the `SEASONS` Script Property: `{id, name, date, db, penalty, state, createdAt, openedAt, closedAt}`, state `created` -> `open` -> `closed` (or `created` -> `closed` for a season created by mistake, which frees its database), never back. `db` (1-5) is the pre-built database it plays (`site/season-<db>.*`, gitignored, built by every deploy); a new season takes a never-used database, else the one closed longest ago. The admin page creates, opens and closes them (never edits any other field: a wrong season is closed and created again; only the name may change, see `rename`) with the passphrase as `key` (`ADMIN_KEY`). It also deletes a season that is not open (owner, 2026-10-25): admin action `delete`, under the script lock, refused while open, removes the record from `SEASONS` and every log row of that season (bottom-up `deleteRows` per run of adjacent rows, never a rewrite of the range, which would turn text cells such as "007" back into numbers), returns `{ok, removedRows}`, and frees its database for `pickDb_`; the desk's bin button ("Delete the season", created and closed rows only) asks in `#ask` (`deleteMessage`: the player count, the CSV export suggested first). It also renames any season, in any state (owner, 2026-10-25): admin action `rename` {season, name}, key and script lock, the name checked as on create (`name_`: 1 to 60 characters after trimming), only `name` changes (id, database, rows untouched); the desk's pencil button ("Rename the season", every row) asks in `#rename` (a labelled field prefilled with `.value`, Enter = Rename, Escape/Cancel = nothing), then reloads the table and the detail. The board and the game read the name from `?meta` (the game keeps `state.seasonName` and re-reads it on boot; the board stops polling once closed, so a board already open on a closed season shows the new name only after a reload).
- Entry: `index.html?season=<id>&board=<Apps Script /exec URL>`. Boot reads `?meta=<id>` (an unknown season and an unreachable backend read differently on the landing); Join posts `join` (refused: `pseudo taken`, `session closed`, `busy, try again` when the script lock is held, retried once after 2 s, then "press Join again"); a created season shows the waiting card, which polls `?meta` 5 s after each answer; the clock runs from `openedAt` (`state.startedAt` = `clockStart(meta)`: `?meta` and the join reply carry the server's `now`, so a wrong browser clock cancels out), so every clock starts together and a late joiner's already runs. Without the link, a reload resumes an unfinished game only while its season is not closed. A reload resumes from `ritz.compete` (season id, team, token, db, board, openedAt) and re-reads `?meta` once. The masthead reads "Season: <name>"; while the season is open and the player has not finished, the game polls `?meta` every 30 s (`watchOn`), and a closed reply (or a post refused with `session closed`) freezes the clock at `closedAt`, adds THE SESSION IS OVER and opens the `#closed` pop-up (a native `<dialog>` in `#part2`'s look: THE SESSION IS OVER, the teacher closed the session, the frozen masthead line, a See the results link to `resultsLink(board, season)` = `leaderboard.html?data=<board>&season=<id>` in a new tab, and Keep reading), once per close (`state.closedSeen`; a reload that finds the season closed shows it then), never after a finish (the finish screen links the same board); the `#taunt` slip is only the fallback where `showModal` is missing; the game stays playable.
- `RANKS` (`badges.js`) and `TAUNTS` (`app.js`) are constants; `PENALTY.wrong` comes from the season record. The in-game `?admin` panel keeps the chapter jumps, the board URL field and a link to `admin.html?board=<url>`.
- Backend (`apps_script.gs`): every POST is validated (pseudo 1-40 chars, chapter 0-8, wrong 0-2000, queries 0-20000, `clientAt` and `elapsedMs` non-negative integers or an empty cell); the pseudo and season id are written as text (a leading apostrophe), so the Sheet never turns "007" into 7 or a pseudo into a formula; any exception comes back as `{ok:false, error}` JSON; `join` returns a token (HMAC of `teamKey|season id`, `TOKEN_SECRET` or `ADMIN_KEY` or `SHEET_ID`) that `progress` and `finish` carry, accepted only while the season is open; a `finish` needs seven `progress` rows first; a script lock guards join (the duplicate check and the append, then `SpreadsheetApp.flush()`) and the admin writes; `create` makes the log tab, so joins never race to create it. `test_backend.mjs` runs the script against stubs. Rows keep the Sheet's columns (`season` holds ids, `hints` always 0). A refusal (`ok:false`) drops the row; only network failures retry.
