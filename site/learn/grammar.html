The Grammar of SQL

Game: the terminal of every chapter

A handful of rules that every correct query follows: what a grouped query may show, how text and names are quoted, how values of different types are compared, what makes a condition.

The game's terminal follows PostgreSQL's rules, and on types it adds one rule of its own: a query that breaks one does not run, and the terminal answers with an error line in PostgreSQL's words and a sentence on how to fix it. The query still counts, but it is not kept in the History list. This page gives the order in which a query is worked out, from which most of the rules follow, then lists every rule with a link to the page that explains it, with examples on the bakery database.

Order of execution

A query is written starting with SELECT, but it is not worked out in that order. Logically, the database takes the clauses in this order, and each step sees only what the step before it produced:

  1. FROM and JOINgathers the rows of the tables and pairs them up
  2. WHEREkeeps the rows whose condition is true
  3. GROUP BYgathers the remaining rows into groups
  4. HAVINGkeeps the groups whose condition is true
  5. SELECTworks out the columns of the result, window functions included, and names them
  6. DISTINCTremoves the rows of the result that repeat
  7. ORDER BYsorts the result
  8. LIMIT and OFFSETkeeps a slice of the sorted rows

Most of the rules on this page follow from that order. An alias is a name given at step 5, so WHERE and HAVING, at steps 2 and 4, run before it exists and cannot use it (see Aliases in WHERE and HAVING), while ORDER BY, at step 7, can (PostgreSQL also lets GROUP BY name an alias, an exception to this order). A window function is computed at step 5 too, which is why it cannot be filtered in WHERE: compute it in a CTE and filter outside. After step 3 each row is a group, so steps 4 to 7 may only use grouped columns and aggregates, plus, in ORDER BY, the result's own column names. And LIMIT comes last, so it keeps the first rows of the sorted result, never a sample taken before sorting. With UNION, INTERSECT or EXCEPT, each half runs steps 1 to 6 on its own, the two results are combined, and the one ORDER BY and LIMIT apply to the combination. The database may take shortcuts when it actually runs a query, but the result is always the one this order gives.

The rules, and where each is explained

Each rule sits on the page of the construct it belongs to, with a query that breaks it, the terminal's answer, and the correct version. The terminal's own error messages link to the same sections.

SELECT and WHERE

  • Double quotes'text' is a value, "name" a name, and a quoted name keeps its case.
  • One equals signSQL compares with =, never ==.
  • TypesA number against a number, text against text, || on text.
  • Aliases in WHERE and HAVINGA SELECT name does not exist there yet.
  • ConditionsWHERE, HAVING, ON and WHEN need something true or false.

ORDER BY and LIMIT

  • DISTINCT and ORDER BYSort by what was selected.
  • LIMIT and OFFSETLIMIT 3 OFFSET 2, not LIMIT 2, 3.

LIKE and text patterns

  • LIKE and ILIKEThe only pattern matches, case-sensitive or not.

Dates and times

  • Dates, substr and CASTComparisons, substr and CAST, not strftime or date(d, '+1 day').

GROUP BY, aggregates and HAVING

  • GROUP BYEvery column grouped or aggregated.
  • HAVING without GROUP BYAggregates only.
  • ORDER BY after GROUP BYGrouped columns, aggregates or aliases.
  • string_agg and SUMNot GROUP_CONCAT or TOTAL.

NULL and missing values

  • COALESCE and ISNot IFNULL; IS only with NULL, TRUE or FALSE.

CASE WHEN

  • CASE, not IIFNo IIF, and no MAX or MIN of two values.
