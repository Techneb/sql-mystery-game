The Grammar of SQL

Game: the terminal of every chapter

A handful of rules that every correct query follows: what a grouped query may show, how text and names are quoted, how values of different types are compared, what makes a condition.

The game's terminal follows PostgreSQL's rules: a query that breaks one does not run, and the terminal answers with PostgreSQL's error line and a sentence on how to fix it. The query still counts, but it is not kept in the History list. Each section below shows a query that breaks a rule, the terminal's answer, and the correct version, on the bakery database.

GROUP BY: grouped or aggregated

After GROUP BY, each row of the result stands for a whole group. A column in SELECT must therefore be one of the grouped columns, or sit inside an aggregate such as COUNT, SUM, MIN or MAX: anything else has several values inside one group, and no single one of them to show.

SELECT category, name, COUNT(*)
FROM product
GROUP BY category;
ERROR: column "product.name" must appear in the GROUP BY clause or be used in an aggregate function Each row of the result is one group, and product.name can hold several values inside a group: add product.name to GROUP BY, or wrap it in an aggregate such as MAX(product.name).
SELECT category, COUNT(*) AS products, MIN(name) AS first_name
FROM product
GROUP BY category
ORDER BY category;
categoryproductsfirst_name
bread4Baguette
cake3Carrot cake slice
pastry3Almond croissant

The same rule applies without GROUP BY: an aggregate turns the whole table into one row, so SELECT category, COUNT(*) FROM product is wrong too, and so is SELECT * with GROUP BY. One exception: when you group by a table's primary key, every other column of that table has a single value per group, so you may select them.

SELECT c.id, c.name, COUNT(*) AS orders
FROM customer AS c
JOIN orders AS o ON o.customer_id = c.id
GROUP BY c.id
ORDER BY orders DESC, c.id
LIMIT 3;
idnameorders

HAVING without GROUP BY

HAVING filters groups. Without GROUP BY, the whole table is one group, so only aggregates make sense in it: a plain column has no single value.

SELECT category
FROM product
HAVING COUNT(*) > 3;
ERROR: column "product.category" must appear in the GROUP BY clause or be used in an aggregate function HAVING without GROUP BY makes the whole table one group, so product.category can only appear inside an aggregate: add GROUP BY product.category, or move a row condition to WHERE.
SELECT category
FROM product
GROUP BY category
HAVING COUNT(*) > 3
ORDER BY category;
category
bread

A query that only selects aggregates may keep its HAVING without GROUP BY: it returns the single row of the whole table, or nothing.

SELECT COUNT(*) AS products
FROM product
HAVING COUNT(*) > 3;
products
10

ORDER BY after GROUP BY

Sorting happens after grouping, so ORDER BY follows the same rule as SELECT: a grouped column, an aggregate, or an alias from the SELECT list.

SELECT category, COUNT(*) AS products
FROM product
GROUP BY category
ORDER BY price DESC;
ERROR: column "product.price" must appear in the GROUP BY clause or be used in an aggregate function After GROUP BY each row is a group, so ORDER BY can only use grouped columns, aggregates or SELECT aliases: sort by MAX(product.price), or add product.price to GROUP BY.
SELECT category, COUNT(*) AS products
FROM product
GROUP BY category
ORDER BY MAX(price) DESC;
categoryproducts
bread4
cake3
pastry3

Say which price you mean: the dearest of each category here, or MIN(price), or AVG(price).

DISTINCT and ORDER BY

SELECT DISTINCT removes repeated rows before the sort, so the sort can only use what was selected.

SELECT DISTINCT category
FROM product
ORDER BY price;
ERROR: for SELECT DISTINCT, ORDER BY expressions must appear in select list DISTINCT removes repeated rows before sorting, so price is gone by then: add it to the SELECT list, or sort by a column you selected.
SELECT category
FROM product
GROUP BY category
ORDER BY MIN(price);
category
bread
pastry
cake

GROUP BY also keeps one row per category, and it lets you sort the categories by an aggregate, here their cheapest product.

Double quotes

Single quotes make a text value: 'bread'. Double quotes make a name, of a column or a table: "category". So "bread" asks for a column called bread, and there is none. Names in double quotes also keep their exact case, so "Category" is not category.

SELECT name
FROM product
WHERE category = "bread";
ERROR: column "bread" does not exist "bread" in double quotes is the name of a column, and there is none: a text value takes single quotes, 'bread'.
SELECT name
FROM product
WHERE category = 'bread'
ORDER BY id;
name
Baguette
Sourdough loaf
Rye loaf
Seeded rolls

The same goes for aliases: an alias is a name, so write AS total, or AS "Total" to keep a capital or a space, never AS 'total'. Names are quoted with double quotes only, not with backticks or square brackets.

One equals sign

SQL compares with a single =. The double == belongs to programming languages, not to SQL.

SELECT name
FROM product
WHERE id == 4;
ERROR: operator does not exist: integer == integer SQL compares with a single equals sign: write id = 4.
SELECT name
FROM product
WHERE id = 4;
name
Croissant

Not equal is <> or !=; both are accepted.

Types

Every column has a type, written in the schema: whole numbers (INTEGER), text (TEXT). A number is compared with a number, text with text; a comparison of two different kinds is an error. So a number is written without quotes, a text value with them, and LIKE only works on text. SUM and AVG need numbers too.

SELECT name
FROM customer
WHERE referred_by = '1';
ERROR: operator does not exist: integer = text referred_by holds numbers and '1' is quoted text: drop the quotes, as in referred_by = 1.
SELECT name
FROM customer
WHERE referred_by = 1
ORDER BY id;
name
Ben Okafor
Chloe Martin

The other way round, a text column against a number, such as day = 20260302, is just as wrong: day holds text, so write day = '2026-03-02', in the column's own format. To use digits stored as text as a number, convert them first with CAST(... AS INTEGER). (Some databases read a quoted number as a number on their own; write it bare, and the type shows in the query.)

Aliases in WHERE and HAVING

An alias given in SELECT (AS double_price) names a column of the result. WHERE and HAVING are worked out before the result exists, so they cannot use it: repeat the expression instead. ORDER BY and GROUP BY may use an alias, but only on its own, not inside a larger expression.

SELECT name, price * 2 AS double_price
FROM product
WHERE double_price > 7;
ERROR: column "double_price" does not exist double_price is a name given in SELECT, and WHERE is worked out before SELECT, so the name does not exist there yet: repeat the expression itself, price * 2.
SELECT name, price * 2 AS double_price
FROM product
WHERE price * 2 > 7
ORDER BY double_price DESC, id;

Conditions

WHERE, HAVING, ON and each WHEN of a CASE need a condition, something true or false. A bare column such as WHERE referred_by is a value, not a condition: write the comparison out. The same holds for each side of AND and OR, and for NOT.

SELECT name
FROM customer
WHERE referred_by;
ERROR: argument of WHERE must be type boolean, not type integer WHERE needs a condition that is true or false, and referred_by is a number: compare it with something, as in referred_by = ... or referred_by IS NOT NULL.
SELECT name
FROM customer
WHERE referred_by IS NOT NULL
ORDER BY id;

Standard syntax

Some shorthands of a single database are not SQL anywhere else. Write the standard form.

SELECT name, price
FROM product
ORDER BY price DESC, id
LIMIT 2, 3;
ERROR: LIMIT #,# syntax is not supported LIMIT 2, 3 is not standard SQL: write LIMIT 3 OFFSET 2 (the row count first, then how many rows to skip).
SELECT name, price

LIKE and ILIKE

LIKE is case-sensitive: a capital letter in the data must be a capital in the pattern. Nothing is wrong with the query below, but a pattern in the wrong case quietly finds nothing.

SELECT name
FROM product
WHERE name LIKE 'croissant%';
name

ILIKE is the same match with case ignored.

SELECT name
FROM product
WHERE name ILIKE 'croissant%'
ORDER BY id;
name
Croissant
