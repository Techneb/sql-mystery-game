Window functions: RANK and LAG

Game: chapters VIII and XI

An aggregate squeezes many rows into one. A window function looks at many rows too, but keeps every row and writes its answer beside it.

The idea of a window

Suppose you want each customer's orders numbered first, second, third, in date order. GROUP BY cannot do it, because it collapses each customer into a single row. A window function computes a value for every row using a set of related rows, its window, and leaves the rows as they are.

The window is described by OVER (...) right after the function. Inside the parentheses, PARTITION BY splits the rows into independent groups (one per customer, say), and ORDER BY sets the order inside each group. Both parts are optional: an empty OVER () means "all rows, in no particular order". Window functions need SQLite 3.25 or later, which every current browser and Python ships. The examples use the bakery database from the bakery database page.

Numbering and ranking

Three functions give positions. ROW_NUMBER() numbers the rows 1, 2, 3 without gaps or ties. RANK() gives tied rows the same rank and then skips: 1, 1, 3. DENSE_RANK() gives ties the same rank without skipping: 1, 1, 2. They differ only when the ORDER BY value ties, and here two breads cost the same. Which of the two tied rows ROW_NUMBER puts first is not defined unless you add a second sort key.

The example keeps only the breads with WHERE, so one window covers them all. To rank every category separately in one query, write OVER (PARTITION BY category ORDER BY price DESC): the numbering then starts again at 1 in each category.

SELECT category, name, price,
       ROW_NUMBER() OVER (ORDER BY price DESC) AS row_number,
       RANK()       OVER (ORDER BY price DESC) AS rank,
       DENSE_RANK() OVER (ORDER BY price DESC) AS dense_rank
FROM product
WHERE category = 'bread';

A window function cannot appear in WHERE, because windows are computed after the rows have been filtered. To keep, say, only the first order of each customer, compute the number in a CTE or a subquery, then filter on it in the outer query. This "number, then filter" pattern answers every question of the form "the first", "the latest" or "the top two" per group.

WITH numbered AS (
  SELECT customer_id, day, time,
         ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY day, time) AS n
  FROM orders
)
SELECT customer_id, day, time
FROM numbered
WHERE n = 1
ORDER BY customer_id;

Looking at the previous row: LAG

LAG(column) returns the value of that column in the previous row of the window; LEAD(column) returns the next one. Put them side by side with the current value and you can measure the change between consecutive rows: the gap between two visits, the growth from one month to the next. The first row of each partition has no previous row, so LAG returns NULL there. An optional second argument looks further back, and a third gives a default instead of NULL.

SELECT customer_id, day,
       LAG(day) OVER (PARTITION BY customer_id ORDER BY day, time) AS previous_visit
FROM orders
WHERE customer_id IN (1, 3);

Dates written as text cannot be subtracted directly, but SQLite's julianday() turns a date into a number of days, so the difference between two of them is a gap in days. Wrapping the window in a CTE then lets you filter or sort on that gap, for instance to find the longest silence between two visits of the same customer.

WITH visits AS (
  SELECT customer_id, day,
         LAG(day) OVER (PARTITION BY customer_id ORDER BY day, time) AS previous_visit
  FROM orders
)
SELECT customer_id, previous_visit, day,
       julianday(day) - julianday(previous_visit) AS gap_days
FROM visits
WHERE previous_visit IS NOT NULL
ORDER BY gap_days DESC, customer_id
LIMIT 3;

The same technique works with times: ROUND((julianday('2000-01-01 ' || b) - julianday('2000-01-01 ' || a)) * 24 * 60) gives the minutes between two HH:MM values on the same day; the ROUND removes the tiny error left by floating-point arithmetic.

Partitions matter

Forgetting PARTITION BY in a LAG is the classic error: the previous row then belongs to another customer, and the gap you compute is meaningless. Ask yourself, before you write the window, "previous within what?" The answer goes into PARTITION BY, and "previous in which order?" goes into ORDER BY. If the order can tie (two orders on the same day), add a second key so that "previous" is well defined.

Common mistakes

Using a window function in WHERE or HAVING instead of filtering in an outer query. Omitting PARTITION BY, so that the window runs across groups. Omitting the ORDER BY inside OVER, which makes LAG and ROW_NUMBER depend on an arbitrary order. Confusing the ORDER BY inside the window, which drives the computation, with the one at the end of the query, which only sorts the output. Choosing ROW_NUMBER when ties should share a place, or RANK when exactly one row per group is wanted.
