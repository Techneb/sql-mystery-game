LIKE and text patterns

Game: chapter III

When you know part of a value but not all of it, = is too strict. LIKE matches a pattern.

Two wildcards

column LIKE 'pattern' is true when the text in the column fits the pattern. A pattern is ordinary text with two special characters. The percent sign, %, stands for any run of characters, including none at all. The underscore, _, stands for exactly one character. Everything else in the pattern must match as written.

So 'Choc%' means "starts with Choc", '%loaf' means "ends with loaf", and '%croissant%' means "contains croissant anywhere". The examples use the bakery database from the bakery database page.

SELECT name, price
FROM product
WHERE name LIKE '%croissant%'
ORDER BY id;
nameprice
Croissant1.4
Almond croissant2.2

Both the plain croissant and the almond croissant match, even though the word sits at the start of one name and at the end of the other, and even though one is written with a capital letter. That last point deserves its own section.

Case and LIKE in SQLite

In SQLite, LIKE ignores the difference between upper and lower case for the letters A to Z. That is convenient when people type names inconsistently, but it differs from =, which is case-sensitive, and from some other databases: in PostgreSQL, LIKE is case-sensitive and ILIKE is the case-insensitive version. If you need a case-sensitive pattern in SQLite, GLOB does that, with * and ? as its wildcards.

The underscore: a fixed length

The underscore is handy for codes and dates whose shape you know. The pattern '2026-03-0_' matches any of the first nine days of March 2026 and nothing else, because exactly one character must follow the zero. Two underscores require two characters, and so on.

SELECT name, joined
FROM customer
WHERE joined LIKE '2024-0_-0_'
ORDER BY id;
namejoined
Ben Okafor2024-02-03
Emma Novak2024-04-02
Grace Lee2024-06-07

That keeps the customers who joined in the first nine days of any month from January to September 2024. Every value in the column has the same length, so the pattern reads like a template.

Combining a pattern with other conditions

LIKE is a condition like any other, so it combines with AND, OR and NOT. NOT LIKE keeps the rows that do not match. A common pattern is to search broadly with LIKE, then narrow down with an exact filter on another column.

SELECT name, category
FROM product
WHERE name LIKE '%o%'
  AND name NOT LIKE '%loaf%'
  AND category <> 'cake'
ORDER BY id;
namecategory
Croissantpastry
Pain au chocolatpastry
Almond croissantpastry
Seeded rollsbread

Read it step by step: names that contain an "o" somewhere, minus the loaves, minus the cakes.

Searching more than one word

When you are not sure of the spelling, try several patterns joined with OR, each one short: a stem such as '%choc%' catches both "Chocolate eclair" and "Pain au chocolat" at once. Shorter patterns find more rows, longer ones fewer. Searching is a conversation with the data: run a broad pattern, read what comes back, then tighten it.

SELECT name
FROM product
WHERE name LIKE '%choc%' OR name LIKE '%tart%'
ORDER BY id;
name
Pain au chocolat
Lemon tart
Chocolate eclair

A pattern search answers the question "which rows mention this?", but a mention is not proof. A row that contains a word may be about something else entirely, so read the matching rows rather than counting them blindly.

Performance, briefly

A pattern that starts with % forces the database to read every row, because no index can help it find text that may begin anywhere. On a small table that does not matter. On millions of rows it does, and a pattern that begins with fixed text, such as 'Choc%', is much cheaper.

Common mistakes

Using = with a wildcard: name = '%tart%' looks for a name that is literally percent-t-a-r-t-percent, and finds nothing. Forgetting the leading %, so that 'croissant%' misses "Almond croissant". Using the * wildcard of file names or of GLOB inside LIKE. Assuming that LIKE is case-insensitive in every database. Trusting a pattern that is too short: '%a%' matches almost everything.
