UNION, INTERSECT and EXCEPT

Game: chapter XII

A join puts tables side by side. A set operation puts two results one above the other, and keeps all their rows, the rows they share, or the rows of the first that the second lacks.

UNION: one list from two queries

Write two complete SELECT statements and put UNION between them: the result holds the rows of the first followed by the rows of the second, with duplicates removed. Each half can read its own tables and use its own conditions, which is what makes it useful when one WHERE cannot say both things at once.

The examples use the bakery database from the bakery database page, whose week of trade ends with the weekend of Saturday 7 and Sunday 8 March. Say the bakery wants to post a leaflet to everyone who lives in Old Town, and to everyone who ordered at the weekend. The first half reads one table, the second needs a join.

SELECT name FROM customer WHERE town = 'Old Town'
UNION
SELECT c.name
FROM customer AS c
JOIN orders AS o ON o.customer_id = c.id
WHERE o.day >= '2026-03-07'
ORDER BY name;

David Chen lives in Old Town and ordered at the weekend, so both halves return him, and Alice Turner ordered twice that weekend; each still appears once. The single ORDER BY at the very end sorts the whole result, not the second half: a set operation takes no ORDER BY or LIMIT inside its halves, only one pair after the last of them.

UNION ALL: keeping every row

UNION ALL stacks the two results as they are. Nothing is compared, so nothing is removed, and it is also the cheaper of the two, since removing duplicates means sorting or hashing every row. Here is the same leaflet list with UNION ALL.

SELECT name FROM customer WHERE town = 'Old Town'
UNION ALL
SELECT c.name
FROM customer AS c
JOIN orders AS o ON o.customer_id = c.id
WHERE o.day >= '2026-03-07'
ORDER BY name;

Alice Turner comes twice from the second half alone, one row per weekend order, and David Chen once from each half. Which one to use depends on the question. For a list of people, UNION. For events you will count or add up afterwards, UNION ALL: two equal amounts on the same day are two payments, and UNION would quietly keep one.

Duplicates are whole rows. Add a column saying why each name is on the list, and David Chen's two rows are no longer equal, so even UNION keeps both. Alice Turner's two weekend rows are still equal, and UNION still merges them.

SELECT name, 'lives in Old Town' AS reason FROM customer WHERE town = 'Old Town'
UNION
SELECT c.name, 'ordered at the weekend'
FROM customer AS c
JOIN orders AS o ON o.customer_id = c.id
WHERE o.day >= '2026-03-07'
ORDER BY name, reason;

Matching the columns

Both halves must return the same number of columns, and the columns are matched by position, not by name: the first column of one goes under the first column of the other, whatever each is called. The result takes its column names from the first half, which is why only the first half above says AS reason. Matched columns should also hold the same kind of value. This timeline of Alice Turner's dealings with the bakery stacks a date from customer on dates from orders, text on text, with a label to tell them apart.

SELECT joined AS day, 'joined' AS event FROM customer WHERE id = 1
UNION ALL
SELECT day, 'ordered' FROM orders WHERE customer_id = 1
ORDER BY day;

A label column like event is the usual companion of UNION ALL: once the rows are stacked, it is the only way left to know which half each came from. The same stacking is the first step of a recursive CTE, whose anchor and recursive part are joined by UNION ALL.

INTERSECT: the rows both results share

INTERSECT keeps only the rows that appear in both results, once each. Which customers ordered during the week and came back at the weekend?

SELECT c.name
FROM customer AS c
JOIN orders AS o ON o.customer_id = c.id
WHERE o.day < '2026-03-07'
INTERSECT
SELECT c.name
FROM customer AS c
JOIN orders AS o ON o.customer_id = c.id
WHERE o.day >= '2026-03-07'
ORDER BY name;
name
Alice Turner
Chloe Martin
David Chen
Emma Novak

A single query with WHERE o.day < '2026-03-07' AND o.day >= '2026-03-07' would return nothing: one order cannot fall on both sides of the date. The question is about two different rows of the same customer, and INTERSECT compares the two lists of names instead of a single row with itself. EXISTS or a self-join can ask the same thing.

EXCEPT: the rows of one but not the other

EXCEPT keeps the rows of the first result that the second does not contain. Which customers ordered during the week but never at the weekend?

SELECT c.name
FROM customer AS c
JOIN orders AS o ON o.customer_id = c.id
WHERE o.day < '2026-03-07'
EXCEPT
SELECT c.name
FROM customer AS c
JOIN orders AS o ON o.customer_id = c.id
WHERE o.day >= '2026-03-07'
ORDER BY name;
name
Ben Okafor
Farid Haddad

Unlike UNION and INTERSECT, EXCEPT is not symmetrical: swap the halves and the question becomes "at the weekend but never during the week", whose answer is Grace Lee alone. It is another way of asking about a missing row, alongside NOT EXISTS and NOT IN on the subqueries page, and unlike NOT IN it treats two NULLs as equal, so a NULL in the second result does not empty the answer.

Names work as the compared column here because no two customers share one. When two different people could have the same name, compare the ids and join the names back afterwards, or the set operation will treat them as one.

Common mistakes

Halves with a different number of columns, which every database refuses. Columns in a different order in each half, which runs and stacks towns under names. A text column matched with a number, which PostgreSQL refuses and SQLite quietly stacks. An ORDER BY at the end of the first half, which is a syntax error: the only one goes after the last half. Using UNION where duplicates are real events to count, or UNION ALL where a list of people was meant. Chaining several different operators without thinking about the order they run in: PostgreSQL works out INTERSECT first, SQLite reads them from left to right, so name each step in a CTE rather than rely on either.
