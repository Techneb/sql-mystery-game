SELECT and WHERE

Game: chapter I

Every SQL query starts here: say which columns you want, from which table, and which rows to keep.

Reading a table

A relational database stores its data in tables. A table has named columns, and each row is one record: one customer, one product, one order. To read a table you write a SELECT statement. The words after SELECT name the columns you want back, and the word FROM names the table they come from. The star, *, means every column, in the order the table defines them.

The examples on this page, like every page of the handbook, run on the small bakery database described on the bakery database page. Its product table lists ten things the bakery sells.

SELECT name, price
FROM product;

The order of the columns in the result is the order you wrote them, not the order in the table. You may also compute a new column and give it a name with AS. The name you choose is an alias: it labels the column in the result and changes nothing in the table.

Keeping only some rows: WHERE

Most of the time you do not want the whole table. The WHERE clause sets a condition, and the database keeps only the rows for which the condition is true. A condition compares a column with a value or with another column, using =, <> (not equal; != also works in SQLite), <, <=, > and >=. Text values go between single quotes; numbers do not.

SELECT name, price, price * 2 AS two_of_them
FROM product
WHERE category = 'pastry';
namepricetwo_of_them
Croissant1.42.8
Pain au chocolat1.63.2
Almond croissant2.24.4

Notice that the database reads FROM first, then WHERE, and only then SELECT. That is why the condition can use any column of the table, even one you do not display.

Combining conditions

Conditions combine with AND (both must be true) and OR (at least one must be true), and NOT turns a condition around. AND binds more tightly than OR, exactly as multiplication binds more tightly than addition, so when you mix them, add parentheses to say what you mean. Two shortcuts save typing: IN (...) tests against a list of values, and BETWEEN a AND b tests a range that includes both ends.

SELECT name, category, price
FROM product
WHERE (category = 'bread' OR category = 'cake')
  AND price BETWEEN 3 AND 4;

Dates in SQLite are usually stored as text in the form YYYY-MM-DD. Because that form sorts in calendar order, you can compare dates as ordinary text: day >= '2026-03-05' keeps every order from the fifth of March onwards. The same is true of times written HH:MM with a leading zero.

SELECT id, customer_id, day, time
FROM orders
WHERE day IN ('2026-03-07', '2026-03-08')
  AND time < '12:00';

Missing values: IS NULL

A column may hold no value at all. SQL writes that as NULL, which means "unknown" rather than zero or an empty string. Nothing is ever equal to NULL, not even another NULL, so referred_by = NULL keeps no rows. To find missing values, write IS NULL; to exclude them, IS NOT NULL. In the bakery, a customer who came in without a recommendation has no referred_by.

SELECT name, town
FROM customer
WHERE referred_by IS NULL;
nametown

A way of working

Start wide and narrow down. Look at a few rows of the table first, then add one condition at a time and check that each one removes what you expected. When a result is empty, remove the last condition and look at what was there before it. Reading the result after every step is faster than writing a long query and wondering why it returns nothing.

Common mistakes

Using double quotes around text: in SQL, 'bread' is a value, while "bread" is the name of a column, and SQLite only falls back to treating it as text when no such column exists, which hides the error until the day it does not. Writing = NULL instead of IS NULL. Forgetting parentheses when mixing AND and OR, which silently changes the meaning. Comparing text with the wrong case: 'Bread' is not equal to 'bread'. Writing a date in another form, such as '5/3/2026', which compares as text and matches nothing.
