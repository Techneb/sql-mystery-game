CTEs and WITH RECURSIVE

Game: chapters VIII, IX and XII

Long queries are easier to write, read and check when they are built in named steps. A CTE is a named step.

WITH: naming a result

A common table expression, or CTE, is a query given a name at the top of a statement with WITH name AS (...). The rest of the statement can then use that name as if it were a table. Nothing is stored: the CTE exists only for the duration of the query. Its value is in the reading. Instead of a subquery buried three levels deep, you get a list of steps, each with a name that says what it holds.

The examples use the bakery database from the bakery database page. Here the first step computes the value of each order line, and the main query adds those values up per order and keeps the larger orders.

WITH line AS (
  SELECT oi.order_id, oi.quantity * p.price AS amount
  FROM order_item AS oi
  JOIN product AS p ON p.id = oi.product_id
)
SELECT order_id, ROUND(SUM(amount), 2) AS total
FROM line
GROUP BY order_id
HAVING SUM(amount) >= 7
ORDER BY total DESC;

Several steps, and joining a CTE

Separate several CTEs with commas, under a single WITH. Each step can use the ones defined before it, and the final query can join them like ordinary tables. This is how a question with several parts becomes manageable: compute one fact per step, check each step on its own by selecting from it, then combine.

WITH order_total AS (
  SELECT oi.order_id, SUM(oi.quantity * p.price) AS total
  FROM order_item AS oi
  JOIN product AS p ON p.id = oi.product_id
  GROUP BY oi.order_id
),
customer_total AS (
  SELECT o.customer_id, COUNT(*) AS orders, SUM(t.total) AS spent
  FROM orders AS o
  JOIN order_total AS t ON t.order_id = o.id
  GROUP BY o.customer_id
)
SELECT c.name, ct.orders, ROUND(ct.spent / ct.orders, 2) AS average_order
FROM customer_total AS ct
JOIN customer AS c ON c.id = ct.customer_id
ORDER BY average_order DESC
LIMIT 3;

To debug such a query, replace the final SELECT with SELECT * FROM order_total and look at the intermediate result. Then do the same with the next step. A mistake usually shows up at the first step whose rows look wrong.

CTEs pair naturally with window functions: compute a rank or a previous value in a CTE, then filter on it outside, since a window function cannot appear in WHERE.

WITH RECURSIVE: following a chain

Some questions have no fixed number of steps. "Who referred the person who referred this customer, and so on, all the way up?" might take one join or ten. A recursive CTE handles that. It has two parts joined by UNION ALL: an anchor, which produces the starting rows, and a recursive part, which refers to the CTE itself and produces the next rows from the previous ones. The database runs the anchor, then runs the recursive part again and again on the newest rows until it produces nothing.

In the bakery, customer.referred_by points to the customer who recommended the shop. Starting from the customers who came on their own, each round adds the people they referred, one generation further down.

WITH RECURSIVE tree(id, name, generation) AS (
  SELECT id, name, 0 FROM customer WHERE referred_by IS NULL
  UNION ALL
  SELECT c.id, c.name, t.generation + 1
  FROM customer AS c
  JOIN tree AS t ON c.referred_by = t.id
)
SELECT name, generation FROM tree ORDER BY generation, id;

Carrying extra columns through the recursion is a useful trick. A counter such as generation tells you how far each row is from the start, and a text column built up with || can record the whole path, which is often the answer you actually want.

WITH RECURSIVE: generating rows

A recursive CTE does not need a table at all. It can count, or produce every date of a period, which is handy for finding days that are missing from the data. The anchor gives the first date, the recursive part adds one day, and a condition in its WHERE stops the recursion.

WITH RECURSIVE calendar(day) AS (
  SELECT '2026-03-02'
  UNION ALL
  SELECT date(day, '+1 day') FROM calendar WHERE day < '2026-03-08'
)
SELECT cal.day, COUNT(o.id) AS orders
FROM calendar AS cal
LEFT JOIN orders AS o ON o.day = cal.day
GROUP BY cal.day;

The left join keeps the day on which nobody ordered, with a count of zero; grouping the orders table alone would simply have skipped it.

Common mistakes

Forgetting the stop condition, so that the recursion never ends: always make sure each round moves towards a limit, and while experimenting add a depth counter with a condition such as WHERE generation < 20. Following a chain that loops back on itself, which also never ends unless the path is tracked. Using UNION where UNION ALL is meant, or the reverse, without thinking about duplicates. Putting the recursive reference in a subquery or an aggregate, which SQLite does not allow. Writing the anchor and the recursive part with a different number of columns.
