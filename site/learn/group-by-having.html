GROUP BY, aggregates and HAVING

Game: chapters IV and VI

So far every query returned rows of the table. Aggregates return facts about many rows at once: how many, how much, the largest, the average.

Aggregate functions

Five functions do most of the work: COUNT, SUM, AVG, MIN and MAX. Used without grouping, each one collapses the whole result into a single row. COUNT(*) counts rows; COUNT(column) counts the rows where that column is not NULL; COUNT(DISTINCT column) counts the different values. The examples run on the bakery database from the bakery database page.

SELECT COUNT(*) AS products,
       MIN(price) AS cheapest,
       MAX(price) AS dearest,
       ROUND(AVG(price), 2) AS average
FROM product;

101.24.52.84

One row per group: GROUP BY

GROUP BY splits the rows into groups that share the same value in one or more columns, then computes each aggregate once per group. The result has one row per group. Picture the database sorting the rows into piles, one pile per category, and then counting or adding up each pile separately.

SELECT category, COUNT(*) AS products, ROUND(AVG(price), 2) AS average_price
FROM product
GROUP BY category;
categoryproductsaverage_price
bread43.32
cake33.3
pastry31.73

The rule to remember: every column in SELECT should either appear in GROUP BY or sit inside an aggregate. Here category is the grouping column and the other two are aggregates. If you add name to the list, the question no longer makes sense (which name, out of four breads?). Most databases refuse such a query; SQLite accepts it and quietly picks a value from one of the rows, which is worse, because the answer looks plausible.

Grouping by more than one column

Grouping by two columns makes one group per combination that actually occurs. Counting orders per customer and per day, for instance, gives one row for each customer on each day they came in. A day on which a customer did not come in produces no row at all: groups are built from the rows that exist, never from the ones that might have.

Filtering groups: HAVING

WHERE filters rows before they are grouped. HAVING filters groups after they are counted, so it is the place for conditions on an aggregate, such as "customers with at least two orders". You cannot write WHERE COUNT(*) >= 2, because when WHERE runs, the counting has not happened yet.

SELECT customer_id, COUNT(*) AS orders
FROM orders
GROUP BY customer_id
HAVING COUNT(*) >= 2
ORDER BY orders DESC, customer_id;

Both clauses can appear in the same query, each doing its own job. The next example keeps only the morning orders (a row filter, so WHERE), groups them by day, and keeps the days with more than one morning order (a group filter, so HAVING).

SELECT day, COUNT(*) AS morning_orders
FROM orders
WHERE time < '12:00'
GROUP BY day
HAVING COUNT(*) > 1;

Adding up quantities

SUM adds the values of a column within each group. In the bakery, the order_item table says how many of each product went into each order, so summing quantity per product gives the number of pieces sold during the week. Sorting by the sum shows the best sellers first. To turn quantities into money you need the price, which lives in another table: that is the job of a JOIN, and the JOIN page finishes this example.

SELECT product_id, SUM(quantity) AS pieces, COUNT(*) AS lines
FROM order_item
GROUP BY product_id
HAVING SUM(quantity) >= 4
ORDER BY pieces DESC, product_id;

The order in which a query runs

It helps to know the logical order: FROM, then WHERE, then GROUP BY, then HAVING, then SELECT, then ORDER BY, then LIMIT. Each step only sees what the previous one produced. That order explains most of the rules on this page.

Common mistakes

Putting an aggregate condition in WHERE instead of HAVING. Putting a plain row condition in HAVING: it may work, but it filters late and reads badly. Selecting a column that is neither grouped nor aggregated, which SQLite allows and fills with an arbitrary value. Using COUNT(column) when you meant COUNT(*) and losing the rows where the column is NULL. Expecting a group for something that has no rows: a product that was never ordered simply does not appear when you group order_item.
